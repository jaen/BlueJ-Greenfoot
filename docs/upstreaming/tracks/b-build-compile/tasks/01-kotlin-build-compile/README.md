# PR-3: Kotlin Build, Compilation, and Workbench

## Goal

Add Kotlin compilation, file handling, and workbench support. Introduce the `LanguageSupport` interface skeleton and `LanguageRegistry` that subsequent PRs extend.

## Prerequisites

None. This is a Phase 1 PR — can start immediately.

## Contents

Mostly porting from PoC (`kotlin-cleanup`) and the upstream `kotlin` branch (Neil/Vitalij), with DI integration and cleanup.

### Dependencies

- Add `kotlin-compiler-embeddable` + `kotlin-stdlib` dependencies to `build.gradle`

### Kotlin compilation

- **`KotlinCompiler.java`** — wraps `K2JVMCompiler`, translates Kotlin compiler diagnostics to BlueJ's `Diagnostic` format

### File handling

- **`KotlinSourceFilter.java`** — file filter for `.kt` files
- **`KotlinFileFacadeRole.java`** — role for `FooKt` facade classes generated by the Kotlin compiler for top-level functions
- Kotlin file templates (`.tmpl` files for new class creation dialogs)

### Class context

- **`KotlinContext.java`** — Kotlin-specific class context handling
- **`KotlinContextFactory.java`** — factory for creating Kotlin contexts

### Reflection utilities

- **`KotlinMetadataReader.java`** — reads Kotlin metadata annotations from compiled classes
- **`KotlinReflective.java`** — Kotlin-aware reflection utilities

## DI integration

### `LanguageSupport` interface

Introduced as a skeleton — just `getCompiler()` initially. The interface shape grows organically as subsequent PRs add methods:

```java
public interface LanguageSupport {
    // PR-3:
    Compiler getCompiler();
    // PR-4 will add: SourceParser createParser(...)
    // PR-5 will add: TokenStream createLexer(SourceFile source)
    // Future: completionProviderFor(), highlighterFor(), etc.
}
```

### `LanguageRegistry`

- `@ProjectScoped` registry mapping `SourceType` -> `LanguageSupport`
- **`JavaLanguageSupport`** wraps the existing Java compilation path
- **`KotlinLanguageSupport`** provides `KotlinCompiler`
- Any component needing language-dependent behavior injects `LanguageRegistry` and asks for the right implementation

### Guice wiring

Both `JavaLanguageSupport` and `KotlinLanguageSupport` are registered in the Guice module, bound into `LanguageRegistry`. The registry itself is `@ProjectScoped`.

## Open questions

1. **Should `LanguageSupport` be an interface or an abstract class?**
   Interface is cleaner and more flexible (allows multiple inheritance if needed), but an abstract class could provide shared utility methods. Lean toward interface with a default methods where appropriate.

2. **Exact shape of `LanguageRegistry` — should it use Guice `MapBinder` or a manual map?**
   `MapBinder<SourceType, LanguageSupport>` is idiomatic Guice and makes adding new languages trivial. A manual map in the registry class is simpler but less extensible. Decide during implementation.
